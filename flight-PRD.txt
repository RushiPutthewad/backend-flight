# Flight Booking System Project Requirements

Build a flight-only booking management system using Node.js, Express.js, MongoDB, Redis, and JWT authentication.

The system allows authenticated users to:

- Search for available flights.
- View flight details.
- Create flight bookings.
- View active and past bookings.
- Cancel eligible bookings.
- Create and manage personal flight-related tasks.
- Track the progress of booking-related work.

# Flight Booking System Architecture

## 1. Application Flow and Architecture

The application follows a layered REST API architecture.

```text
Client
  |
  v
Express Router
  |
  v
Authentication and Validation Middleware
  |
  v
Controller
  |
  v
Service Layer
  |
  +--> MongoDB Repositories
  |
  +--> Redis Cache
  |
  +--> Payment Service
  |
  +--> Flight Availability Service
```

### Request Flow

1. The client sends an HTTP request.
2. Express receives the request.
3. Middleware handles:
   - Request logging.
   - CORS.
   - JSON parsing.
   - Authentication.
   - Rate limiting.
   - Validation.
4. The router maps the request to a controller.
5. The controller extracts validated request data.
6. The service layer applies business rules.
7. Repositories communicate with MongoDB.
8. Redis is checked or updated when caching applies.
9. The controller returns a consistent response.
10. Errors are passed to centralized error middleware.

### Authentication Flow

```text
Register
  -> Validate input
  -> Hash password
  -> Store user
  -> Return account response

Login
  -> Find user
  -> Compare password
  -> Issue JWT
  -> Return token

Protected request
  -> Read Authorization header
  -> Verify JWT
  -> Attach user to request
  -> Continue to controller
```

### Flight Search Flow

```text
Client
  -> GET /flights/search
  -> Validate search parameters
  -> Create normalized cache key
  -> Check Redis
      -> Cache hit: return cached results
      -> Cache miss: query MongoDB
  -> Store results in Redis with expiration
  -> Return results
```

### Booking Flow

```text
Client
  -> POST /bookings
  -> Authenticate user
  -> Validate passengers and flight data
  -> Start database transaction
  -> Verify flight availability
  -> Reserve seats
  -> Create pending booking
  -> Process payment
  -> Confirm or fail booking
  -> Commit or roll back transaction
  -> Invalidate related cache
  -> Return booking
```

Seat availability must be checked against MongoDB within a transaction or another concurrency-safe mechanism. Redis may assist with temporary locks, but it must not replace the database consistency check.

### Cancellation Flow

```text
Client
  -> PATCH /bookings/:id/cancel
  -> Authenticate user
  -> Verify booking ownership
  -> Verify cancellation eligibility
  -> Update booking status
  -> Restore seat inventory
  -> Process refund if applicable
  -> Invalidate cache
  -> Return updated booking
```

# Flight Booking System Rules

## 1. What to Use

### Project Scope

- Build flight-only functionality.
- Keep flight search, booking, cancellation, and task tracking separate.
- Use MongoDB as the source of truth.
- Use Redis for caching and short-lived coordination.
- Use JWT for authenticated API access.
- Use RESTful resource-based routes.
- Version the API with `/api/v1`.
- Use UTC for all stored timestamps.
- Use ISO 8601 date and time formats in API requests and responses.
- Use database indexes for common search and ownership queries.
- Use transactions for seat and booking changes where supported.
- Use idempotency keys for booking creation if payment or external services are introduced.
- Use environment variables for secrets and connection strings.
- Use automated tests for business-critical behavior.
- Use centralized error handling.
- Use structured logs without sensitive information.

### API Rules

- Validate all client input.
- Reject unknown or malformed fields where appropriate.
- Return correct HTTP status codes.
- Use consistent response envelopes.
- Paginate list endpoints.
- Enforce ownership checks on every user-owned resource.
- Return generic authentication errors to avoid account enumeration.
- Never trust client-provided prices, totals, booking status, or user IDs.
- Recalculate booking totals on the server.
- Verify flight availability on the server.
- Use explicit status transitions.
- Make cancellation operations safe to repeat.

### Security Rules

- Hash passwords before storage.
- Never store plaintext passwords.
- Keep JWT secrets outside source control.
- Use strong secret values in production.
- Use secure cookie settings if refresh tokens are stored in cookies.
- Apply rate limits to login, registration, search, and booking endpoints.
- Sanitize user-controlled content before rendering it in any frontend.
- Avoid exposing internal stack traces in production responses.
- Do not log passwords, JWTs, passport numbers, or payment details.
- Limit access to administrative routes.
- Use HTTPS in deployed environments.

### Redis Rules

- Use normalized cache keys.
- Set expiration times on all cache entries.
- Invalidate affected cache entries after booking or cancellation changes.
- Treat Redis as disposable.
- Handle Redis outages without corrupting booking data.
- Do not use stale cached availability as the final booking decision.

### MongoDB Rules

- Add indexes for:
  - Flight origin and destination.
  - Flight departure date.
  - Booking user ID.
  - Booking status.
  - Task user ID.
  - Task status and category.
- Avoid unbounded document growth.
- Use projections when returning large collections.
- Use transactions for multi-document booking operations.
- Store references between users, flights, bookings, and tasks.
- Validate enum values at both request and model levels.

## 2. What to Avoid

### Libraries and Architecture

- Do not use unrelated booking libraries that hide core business logic.
- Do not introduce multiple libraries for the same responsibility.
- Do not mix ORM patterns and direct database access without a clear reason.
- Do not put business logic in route files.
- Do not put database queries directly in controllers.
- Do not create a large single-file application.
- Do not use global mutable state for booking data.
- Do not add microservices before the modular monolith is stable.
- Do not add a real payment provider in the first phase unless explicitly required.

### Flight Scope

Do not build:

- Hotel reservations.
- Car rentals.
- Vacation packages.
- Restaurant reservations.
- Train or bus bookings.
- Airline loyalty programs.
- Live aircraft tracking.
- Complex travel insurance workflows.

### Data and Security

- Do not trust prices received from the client.
- Do not trust seat availability received from the client.
- Do not allow users to submit another user's ID to access their resources.
- Do not return password hashes.
- Do not return JWT secrets or environment variables.
- Do not expose full internal database errors.
- Do not store passport information unless the feature requires it and appropriate protection is implemented.
- Do not store payment card numbers.
- Do not use predictable booking references.
- Do not make destructive database operations without authorization.

### Error Handling

- Do not use empty `catch` blocks.
- Do not silently ignore database or Redis failures.
- Do not return HTTP 200 for failed operations.
- Do not expose stack traces in production.
- Do not create different error formats for different routes.
- Do not treat validation errors as server errors.
- Do not retry non-idempotent booking operations without an idempotency strategy.
- Do not mark a booking as confirmed before payment and availability checks succeed.

### Caching

- Do not cache private booking responses without user-aware keys.
- Do not cache sensitive passenger or payment information.
- Do not cache data indefinitely.
- Do not assume a cache hit means data is current.
- Do not allow cache failures to bypass authorization.

## Boundaries for AI-Assisted Development

AI-generated code may be used for:

- Boilerplate route and controller structures.
- Test case scaffolding.
- Documentation drafts.
- Validation schema drafts.
- Repetitive CRUD implementations.
- Refactoring suggestions.

AI-generated code must be manually reviewed for:

- Authentication and authorization.

- Payment state transitions.
- Seat inventory updates.
- MongoDB transactions.
- Redis locking and invalidation.
- Sensitive data handling.
- Error-handling behavior.
- Input validation.
- Race conditions.

AI must not independently decide:

- Production secrets.
- Payment-provider configuration.
- Legal or compliance requirements.
- Data-retention policy.
- Refund policy.
- Authentication token lifetime.
- User roles and administrative permissions.
- Production deployment access.

Every AI-generated change must include:

- Tests for important paths.

- Review of security implications.
- Confirmation that flight-only scope is preserved.

AI output must not be accepted solely because it compiles or passes a happy-path test.

- Use `--color-success` for confirmed bookings and completed tasks.
- Use `--color-warning` for pending payments, upcoming deadlines, and limited availability.
- Use `--color-danger` for cancellation and destructive actions.
- Maintain strong contrast for text and interactive controls.
- Do not use color as the only way to communicate status; pair it with text or icons.

### Status Colors

| Status | Color | Meaning |
|---|---|---|
| Confirmed | Green | Booking is active and paid |
| Pending | Amber | Action or payment is still required |
| Cancelled | Red | Booking or task has been cancelled |
| Completed | Blue | Task has been completed |
| Failed | Red | Operation did not complete |
| Draft | Gray | Data exists but is not finalized |

## 2. Fonts

Use a distinctive but highly readable font pairing.

### Recommended Fonts

- Headings: `Manrope`
- Body text: `Source Sans 3`

#### Manrope

Use for:

## 3. Typography

### Type Scale

```css
:root {
  --text-xs: 0.75rem;
  --text-sm: 0.875rem;
  --text-md: 1rem;
  --text-lg: 1.125rem;
  --text-xl: 1.5rem;
  --text-2xl: 2rem;
  --text-3xl: 3rem;
}
```

### Typography Rules

- Use sentence case for headings and labels.
- Keep headings concise and action-oriented.
- Use tabular or monospaced numerals for flight times and prices.
- Keep body text between `1rem` and `1.125rem` for primary reading content.
- Use a line height of approximately `1.5` for body copy.
- Use tighter line height between `1.1` and `1.25` for large headings.
- Do not use more than three font families.
- Do not use all-caps for long labels.
- Use font weight to establish hierarchy rather than relying only on color.

### Suggested Hierarchy

| Element | Font | Size | Weight |
|---|---|---:|---:|
| Application title | Manrope | 2rem-3rem | 700 |
| Page heading | Manrope | 1.5rem-2rem | 700 |
| Section heading | Manrope | 1.125rem-1.5rem | 700 |
| Body text | Source Sans 3 | 1rem | 400 |
| Form label | Source Sans 3 | 0.875rem | 600 |
| Helper text | Source Sans 3 | 0.875rem | 400 |
| Flight number | IBM Plex Mono | 0.875rem-1rem | 600 |
| Airport code | IBM Plex Mono | 1rem-1.25rem | 600 |
| Booking reference | IBM Plex Mono | 1rem | 600 |

### Layout and Component Guidance

#### Flight Search

- Make origin and destination visually prominent.
- Display airport codes larger than airport names.
- Show departure and arrival times in a clear horizontal or stacked layout.
- Keep search filters easy to modify.
- Show price and availability without hiding them behind secondary actions.

#### Booking Details

- Present booking status at the top.
- Display booking reference with copy functionality.
- Separate passenger, flight, payment, and cancellation information.
- Use clear visual grouping instead of dense tables on mobile.

#### Task Management

- Use status badges with text.
- Support quick status changes.
- Display due dates prominently when approaching.
- Link a task to its booking without making the task interface dependent on booking details.

#### Responsive Behavior

- Desktop layouts may use a sidebar and multi-column cards.
- Tablet layouts should reduce columns without hiding core booking information.
- Mobile layouts should stack flight details vertically.
- Primary actions must remain visible and reachable on small screens.
- Tables should become cards or horizontally scroll only when necessary.

#### Motion

Use restrained motion:

- Fade and slide page sections into view.
- Animate loading placeholders.
- Use a short transition for status changes.
- Avoid decorative animations that delay booking actions.
- Respect `prefers-reduced-motion`.
